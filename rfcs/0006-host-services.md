## 一句话摘要

把"每个全栈插件都在自己重造"的六类宿主能力——HTTP 路由、模型调用、提示词注入、后台任务、文件存储、事件过滤——收进标准，变成 manifest 里声明一行就能用的契约。

## 背景

先看三个真实的故事——都来自对 9 个现役插件的源码审计（2026-08，样本与证据见 [docs-plan.md §8](../docs-plan.md)）。

**故事一：157 MB 的冷启动。** activity 插件想做跨会话统计，需要读会话事件。宿主的读取面不支持事件类型过滤，而一个会话 28,172 条事件里有 27,994 条是逐 token 的原始流 chunk——99.4% 是它根本不关心的数据。100 个会话冷启动下载了 157 MB，插件只能自建本地摘要加游标增量，把二次进入压到 47 ms。这不是插件写得差，是宿主少给了一个过滤参数。

**故事二：三份互相不等价的 home 解析。** tavern、travel、pet 三个插件都需要一个私有数据目录。宿主内部明明有解析逻辑（环境变量优先、兜底 `~/.dsh`），但没有作为服务暴露，于是三个插件各抄一份——优先级规则抄得还不全，pet 甚至直接把文件写进了宿主的根目录。原子写也是同款局面：tmp 加 rename 的模式被抄了四份，还有一个插件干脆没做。

**故事三：家家自造的安检门。** aionui-panel 给文件读写做了工作区前缀校验加符号链接防走私；remote-web-ui 给局域网访问做了回环判定加配对 Cookie；宿主的静态资源包内部还有第三套路径穿越防护。三套门禁，三种写法，三种漏洞面。安全原语让插件各自重造，等于让每个插件作者都当一次安全工程师——大多数人当不好。

这三个故事指向同一个结论：**现在缺的不是能力，宿主什么都有；缺的是契约。** 能力以 cordis 内部服务的形态存在，外部插件要么够不着，要么够着了也没有稳定的、带版本号的、可协商的约定。RFC 0006 就是把这六类能力从"内部服务"扶正为"标准能力"：

| 契约坐标（示意，以 Registry 定案为准） | 管什么 | 今天谁在 hack |
| --- | --- | --- |
| `webserver.dsh/v1alpha1` **WebRoutes** | HTTP/WebSocket 路由注册 | tavern、aionui-panel、git-graph、remote-web-ui |
| `llm.dsh/v1alpha1` **LlmAccess** | 列出并驱动宿主已配置的模型 | tavern（记忆提取、心跳发文） |
| `prompt.dsh/v1alpha1` **PromptSections** | 有序、可按会话条件注入的系统提示词段 | tavern、task-board、aionui-panel |
| `jobs.dsh/v1alpha1` **BackgroundJobs** | 宿主进程内的后台任务与定时调度 | tavern 心跳、task-board 的浏览器 cron |
| `filestore.dsh/v1alpha1` **PluginFiles** | 插件私有数据目录与原子写 | tavern、travel、pet |
| `sessions.dsh/v1alpha1` **SessionFeed** | 服务端过滤的会话事件订阅与游标增量 | activity、tavern |

## 目标

- 六条契约各给出：语义边界、manifest 声明形态、权限与降级语义、以及"官方实现变化时插件不炸"的适配层职责划分。
- 每条契约都回答"谁来实现安全部分"——门禁、校验、配额写进契约，而不是留给插件自由发挥。
- 每条契约都以一个真实插件作为验证样本：tavern 一个插件就能走完其中五条。

## 非目标

- **不重发明已有服务。** 宿主的 cordis 服务是实现，本 RFC 定义的是契约面；契约面刻意小于实现面（见"设计原则"）。
- **不管插件间的服务组合。** 插件向插件提供服务走 [RFC 0003](0003-service-composition.md)，本 RFC 只规范"宿主向插件"。
- **不管跨端渲染。** Node 半区与浏览器半区之间的事件通道属于 RFC 0002 的合流议题，本 RFC 只在 `SessionFeed` 里处理事件过滤这一个点。
- **不定 cron 表达式的具体语法、配额的具体数值。** 这些属于 spec 阶段细节，本 RFC 只定语义。

## 设计

### 设计原则：契约面是 SDK 面，不是内部服务面

这是全篇最重要的一条，先说清楚。

宿主的能力今天是 cordis 服务，明天可能重构、改名、换签名。如果契约直接照抄内部服务，官方一变，下游全炸——这正是本标准存在的理由。所以六条契约定义的都是 **SDK 面**：插件看到的是稳定的、带契约坐标的接口；宿主侧的**适配层**负责把内部服务映射进来。官方重命名了？改适配层。官方换了事件负载？适配层做转换。插件代码一行不动。

由此得到三条推论，适用于全部六条契约：

1. **契约面刻意小于实现面。** 内部服务有二十个方法，契约只收插件真正在用的三四个。收窄的面才好稳定。
2. **负载用契约语言重新定义，不做类型直通。** 例如模型流式产出的事件，契约里用自己的块类型定义（对齐 spec/event-envelope.md 的 ContentBlock 边界），而不是透传宿主内部类型。
3. **每条契约都是协商能力。** 插件在 manifest 的 `requires.contracts` 里声明，required 缺失拒载、optional 缺失降级，语义一律走 spec/negotiation.md，本族不发明新规则。

### 六条契约

#### 1. WebRoutes——HTTP 路由注册

**语义**：插件声明式注册 HTTP 路由。每条路由是 `exact`（精确路径）或 `prefix`（前缀，最长前缀胜出）之一，处理器拥有完整的响应生命周期——允许长挂响应，这正是 SSE 的实现方式。WebSocket upgrade 路由单列，仅支持 exact。

**安全下沉是这条契约的核心**，也是与宿主现状最大的差异。路由声明时必须选择门禁档位，宿主在分发前强制：

| 档位 | 语义 | 适用 |
| --- | --- | --- |
| `loopback`（默认） | 仅本机回环请求可达 | 绝大多数插件路由 |
| `lan-paired` | 局域网请求须持有效配对凭证 | remote-web-ui 类远程访问 |
| `workspace-scoped` | 路径参数必须落在已注册工作区内（宿主做 realpath 前缀校验与符号链接防逃逸） | 文件读写类路由 |

静态资源服务不作为自由路由开放，而是契约内建的助手：声明根目录后由宿主提供，路径穿越防护内建（越界一律 403），不给插件拼路径的机会。

**边界**：不提供中间件框架、不解析请求体、不做鉴权业务逻辑——但回环判定、局域网门禁、工作区围栏、穿越防护这四件事是宿主职责，不再允许插件自造。宿主绑定地址只有 `127.0.0.1` 与 `0.0.0.0` 两档，与现状一致。

**验证样本**：tavern（角色立绘静态路由加 JSON API）、aionui-panel（workspace-scoped 档位）、remote-web-ui（lan-paired 档位）。

#### 2. LlmAccess——宿主内模型调用

**语义**：插件列出宿主已配置的 provider 与模型，并发起流式调用。调用面收敛为三个方法：列 provider、列模型、流式生成。流式产出是契约定义的事件块序列（文本增量、推理增量、工具调用增量、用量、结束原因），对齐 event-envelope 的 ContentBlock 边界。

**三条明确的语义表态**：

- **没有"当前用户模型"解析。** 宿主今天不提供这个，插件自己定默认路由策略（tavern 的现状）。契约保留一个 `resolveDefault` 扩展点但不承诺 v0.16 落地。
- **不做计费与配额。** 用量以 usage 块如实上报，宿主不从它派生任何门控决策——这与宿主现状一致，写进契约是为了防止未来某宿主悄悄加配额炸了插件。
- **调用必须可被观察。** 宿主保留对每次调用的拦截与审计钩子（cordis waterfall 的契约化），这是授权模型的落点：敏感能力不能只声明，还要可审计。

**验证样本**：tavern（记忆提取、朋友圈心跳发文、互评，全部走自发调用）。

#### 3. PromptSections——系统提示词分段注入

**语义**：插件注册一个命名提示词段，带 `order`（升序拼接）与 `text`——`text` 可以是静态字符串，也可以是一个同步函数，在每次组装时求值并拿到组装上下文。返回空串等价于"本次不注入"，这就是按会话条件注入的标准姿势。

order 的数值约定直接转正宿主现行惯例，写进契约防止语义漂移：`-100` 是宿主身份、`0` 是部署人格、`100–199` 是工具指导；插件段默认落在负数区间（人格之前）或 `200+`（工具之后），由插件按语义自选。

**边界**：函数必须同步、必须幂等——它在每次组装时重新求值，副作用会导致不可诊断的行为。独占整个提示词（`complete`）的能力**不收进契约**：它本质上排他，与多插件共存矛盾，等真有需求再单独立案。

**验证样本**：tavern（按会话映射注入角色人格，order -90/-85）。

#### 4. BackgroundJobs——后台任务与定时调度

**语义**：分两层。

**后台任务层**转正宿主的 JobRegistry 形态：插件注册任务种类，启动后得到任务句柄，可列表、增量读输出、终止、等待完成、订阅完成事件。任务归属于会话或游离（无主任务任何调用方可见），访问按会话围栏隔离；句柄可预测这一点要明确写进契约："句柄是授权标识，不是保密标识"。

**定时调度层是本族里唯一超出宿主现状的设计**，必须给足理由：今天插件只有两条路——把定时器塞进浏览器标签页（task-board 的做法，关掉页面就错过触发），或者在宿主进程里裸 `setInterval`（tavern 的做法，没有任何持久化与治理）。契约定义：插件声明调度规则（一次性相对延迟、一次性绝对时刻、固定间隔三档，间隔下限由宿主定，建议 5 分钟，与宿主现行一致），**宿主进程负责触发与持久化**，崩溃重启后补投过期任务。触发负载是唤醒插件的指定激活点，不是直接向会话发消息——向会话发消息是插件被唤醒后自己的选择。

**边界**：cron 表达式语法留给 spec 阶段；进程级守护（插件崩溃不影响宿主调度）依赖 lifecycle 的 effect ledger，不在本条重复定义。

**验证样本**：tavern 的 15 分钟记忆提取与朋友圈心跳、task-board 的定时提醒。

#### 5. PluginFiles——插件私有文件存储

**语义**：宿主为每个插件分配私有目录（逻辑位置 `插件数据根/<插件 id>/`，物理位置由宿主解析规则决定），插件通过注入的句柄读写，**写入一律原子**（tmp 加 rename 内建于实现，插件没有非原子的写法可选）。插件之间互不可见，边界由宿主强制。

这条契约一次性消灭三份互相不等价的 home 解析、四份重抄的原子写、以及"插件把文件写进宿主根目录"这类事故。它同时回答浏览器半区的存储问题：浏览器侧的插件代码经服务通道读写同一目录，不再只有 localStorage 一条路。

**与既有 `storage.dsh/v1alpha1`（LocalStorage）的分工**：键值小数据走 LocalStorage，成文件的数据（JSON 档案、媒体资源、可导出的 Markdown）走 PluginFiles。一条经验法则写进 registry 条目：数据要不要以"一个文件"的形态被用户或 AI 直接看到、改到？要，就是 PluginFiles。

**边界**：跨插件共享文件不做——共享是组合问题，归 RFC 0003。配额与总量限制留给宿主实现，契约只要求超限时报结构化错误。

**验证样本**：tavern（mapping/memory/moments/cards 四组 JSON）、travel（guide.json 加 backups 归档，AI 直接改文件后刷新生效的模式值得写进指南）。

#### 6. SessionFeed——事件过滤与增量同步

**语义**：插件订阅会话事件时声明**事件类型白名单**，宿主在源头过滤，不把 chunk 洪流推给不需要的人。读取历史时同样支持类型过滤加分页。订阅与读取都携带 **seq 游标**：插件记录已处理到的 `asOfSeq`，重连后从游标续拉，语义与 event-envelope 的 scope 内单调序列对齐。

这条契约直接消化 157 MB 事故。activity 插件自建的"摘要加游标"增量模式就是它的原型——把插件踩出来的最佳实践扶正为标准能力，正是本 RFC 的方法论。

**与现有 `messages.dsh/v1alpha1`（MessageObserver）的关系**：MessageObserver 观察"消息"这个领域概念，SessionFeed 是通用的会话事件流。前者保持不变，后者是新增的底层能力；registry 条目里写清楚"只关心消息就用前者，需要原始事件或增量同步才用后者"。

**边界**：过滤是声明式白名单，不支持任意谓词——谓词下推会让宿主实现背上表达式引擎，收益不抵成本。`ignorable` 事件的重建语义不变，仍走 event-envelope 的定义。

**验证样本**：activity（类型过滤加游标增量）、tavern（host 侧只收 user/message 与 assistant/message 两类）。

### 权限与协商

六条契约全部是敏感能力，走同一套规则：

- manifest 声明依赖；`webserver` 与 `llm` 建议同时计入安装影响报告（RFC 0004 的落点），让用户在安装前看见"这个插件会开端口 / 会调模型"。
- WebRoutes 的门禁档位、PluginFiles 的目录边界、SessionFeed 的类型白名单都是**声明即授权**的粒度：声明之外的访问，宿主必须拒绝，且拒绝要产生可诊断的结构化错误。
- optional 声明的降级语义走 negotiation 通则；插件作者指南里要为每条契约给一个"缺失时怎么体面降级"的示例。

## 被拒绝的替代方案

**直接暴露宿主的 cordis 服务给插件。** 最省事，但把契约绑死在实现上：官方重命名一个方法，下游全炸。本标准的存在理由就是隔出适配层。若未来官方服务面冻结多年不变，可以重新考虑直通。

**安全门禁留给插件自律。** 现状就是这个方案，结果是三套互不相同的门禁、三种漏洞面。安全原语是宿主最该下沉的东西。除非某档位被证明无法在宿主侧通用实现，否则不回退。

**把六条契约合成一条"host-services"大契约。** 协商粒度太粗：插件只要文件存储，却被迫声明一个含开端口能力的大契约，安装影响报告会吓到用户。粒度即权限，必须分开。

**定时调度走"唤醒会话发消息"（宿主 schedule 包的现状）。** 那是给模型用的提醒，投递的是会话内消息，插件拿不到执行权。插件要的是"到点跑我的代码"。两条路语义不同，不合并；若未来宿主 schedule 开放插件面，再评估对齐。

**文件存储复用宿主内部的 KV backend registry。** 它服务宿主的 domain 层，抽象目标是可替换存储后端，不是"给插件一个目录"。语义错位，硬复用会两头不讨好。PluginFiles 的实现可以站在它上面，但契约是新的。

## 开放问题

1. **WebRoutes 的 `lan-paired` 配对体系**由谁定义——配对令牌、二维码、设备会话是 remote-web-ui 自造的一整套，收进契约还是留给插件？倾向：契约只定义门禁档位的判定接口，配对流程留给插件，spec 阶段收集反馈。
2. **LlmAccess 的默认模型解析**（`resolveDefault`）要不要进 v0.16？宿主现状没有此概念，契约若先定义，宿主实现需要新造语义。
3. **BackgroundJobs 的间隔下限**定为宿主可配还是契约固定？5 分钟来自宿主现行模型工具约束，对插件是否过严？
4. **SessionFeed 的类型白名单与声明合并**：宿主事件类型表是可扩展的（第三方包可合并新类型），白名单如何引用尚未登记的扩展类型——宽松放行还是严格拒载？
5. **浏览器半区访问 PluginFiles 的通道形态**：走既有 RPC 面还是契约自带传输？与 RFC 0002 的 Transport 分层需要对齐。
6. 六条契约的**命名空间归属**：`webserver.dsh` 还是 `net.http.dsh`？`sessions.dsh` 还是 `events.dsh`？spec 阶段连同 registry 条目一并定案。

## 落地顺序

1. 本 RFC 进 Review 的同时，开出六份 registry 条目骨架（坐标、语义一句话、边界清单），让讨论落在具体坐标上。
2. Accepted 后按条产出 spec：`spec/host-services/` 下每契约一份，附带 schema 与 fixtures（"门禁外访问被拒""非原子写不存在"都要有 fixture）。
3. tavern 作为全栈验证样本改写一遍；activity 的 SessionFeed 改造作为性能证据（157 MB → 增量）。
4. guides/plugin-author.md 增补"你以前的野路子对应哪条契约"对照表；hello-world 教程保持纯声明式，不引入本族能力。
